# Развёртывание Dragram на VPS

Инструкция для переноса проекта на свой сервер. Postgres, Redis, приложение и
nginx живут на самом сервере, файлы — в Yandex Object Storage.

**Бюджет:** ~880 ₽/мес за VPS + ~30 ₽/мес за домен. Object Storage — по объёму,
Let's Encrypt бесплатен.

---

## Что откуда берётся

```
                       интернет
                          │  :443 HTTPS
                   ┌──────▼──────┐
                   │    nginx    │◄── сертификат от certbot (обновляется сам)
                   └──────┬──────┘
                          │  всё, включая /media/ и WebSocket
                   ┌──────▼──────┐
                   │     app     │  FastAPI + собранный фронтенд
                   │  (uvicorn)  │
                   └──┬───┬───┬──┘
        302 на        │   │   │
   presigned-ссылку   │   │   │
   ┌───────────────┐  │   │   │
   │ Yandex Object │◄─┘   │   │
   │Storage(закрыт)│      │   │
   └───────────────┘      │   │
                   ┌──────▼─┐ └─▼──────────────┐
                   │ redis  │  │   postgres    │
                   │ pub/sub│  │  (том Docker) │
                   └────────┘  └───────────────┘
```

Образ приложения собирается **на GitHub Actions**, а не на сервере: сборка
фронтенда через Vite требует ~1.5 ГБ RAM и на VPS с 2 ГБ упала бы с OOM.
Сервер только скачивает готовый образ.

---

## Шаг 1. Покупка сервера

Заказать VPS (например, [Timeweb Cloud](https://timeweb.cloud/)) с параметрами:

| Параметр | Значение |
|---|---|
| ОС | Ubuntu 24.04 |
| CPU / RAM | 2 vCPU / 2 ГБ |
| Диск | 40 ГБ NVMe |
| Локация | Москва или Санкт-Петербург |

При заказе загрузить свой SSH-ключ (не пароль — так безопаснее и удобнее).
Если ключа нет, создать: `ssh-keygen -t ed25519`.

## Шаг 2. Домен

Купить домен и в панели DNS создать **A-запись**, указывающую на IP сервера:

```
Тип: A    Имя: @    Значение: <IP сервера>    TTL: 300
```

Обновление DNS занимает от нескольких минут до пары часов. Проверить:

```bash
nslookup dragram.ru
```

Дальше идти только когда `nslookup` показывает IP сервера — иначе Let's Encrypt
не выдаст сертификат.

## Шаг 3. Настройка сервера

```bash
ssh root@<IP сервера>
```

На сервере:

```bash
apt-get update && apt-get install -y git
git clone https://github.com/doorhanoff/dragram.git /opt/dragram
cd /opt/dragram
sh deploy/bootstrap-server.sh
```

Скрипт ставит Docker, включает файрвол (открыты только 22, 80, 443), добавляет
2 ГБ swap и включает автообновления безопасности.

## Шаг 4. Переменные окружения

```bash
cd /opt/dragram
cp .env.prod.example .env
nano .env
```

Заполнить все поля.

> **Про знак `$` в значениях.** Docker Compose раскрывает `$` в `.env` как
> подстановку переменной: пароль `abc$Odk123` молча превратится в `abc`, и
> приложение не подключится к базе с невнятной ошибкой авторизации. Если в
> сгенерированном пароле такой символ есть — удвоить его: `abc$$Odk123`.
> Проверить, что всё прочиталось правильно:
>
> ```bash
> docker compose -f docker-compose.prod.yaml config | grep DB_PASS
> ```
>
> (в выводе `$` тоже показывается удвоенным — это нормально, внутрь контейнера
> попадёт один).

Отдельно про два поля:

- **`JWT_SECRET_KEY`** — сгенерировать новый, локальный не переносить:
  ```bash
  python3 -c "import secrets; print(secrets.token_urlsafe(64))"
  ```
  После смены ключа все выданные раньше токены станут недействительными —
  пользователям придётся войти заново.
- **`FCM_CREDENTIALS_JSON`** — содержимое service-account JSON одной строкой,
  без переносов.

Закрыть файл от посторонних глаз:

```bash
chmod 600 .env
```

## Шаг 5. Доступ к образу

GitHub Actions собирает образ при каждом push в `master` и кладёт в GitHub
Container Registry. Первая сборка запустится сама после того, как эти файлы
попадут в репозиторий; посмотреть её можно во вкладке **Actions**.

Если репозиторий **приватный**, образ тоже приватный, и серверу нужен доступ:

1. GitHub → Settings → Developer settings → Personal access tokens →
   Tokens (classic) → Generate new token, галочка **`read:packages`**;
2. на сервере:
   ```bash
   echo "<токен>" | docker login ghcr.io -u doorhanoff --password-stdin
   ```

Если репозиторий публичный — шаг можно пропустить, но образ по умолчанию всё
равно приватный: сделать его публичным можно в GitHub → Packages → dragram →
Package settings → Change visibility.

## Шаг 6. Сертификат и запуск

```bash
cd /opt/dragram
sh deploy/init-letsencrypt.sh
```

Скрипт выпустит сертификат Let's Encrypt и поднимет nginx. Затем:

```bash
sh deploy/deploy.sh
```

Готово — проект доступен по `https://<твой домен>`.

## Обновление после изменений в коде

```bash
git push            # локально
```

GitHub Actions соберёт новый образ (~3–5 минут), после чего на сервере:

```bash
cd /opt/dragram && git pull && sh deploy/deploy.sh
```

Миграции Alembic накатываются автоматически при старте контейнера
(см. `entrypoint.sh`).

docker compose -f docker-compose.prod.yaml ps

```bash
docker compose -f docker-compose.prod.yaml logs -f app
```

```bash

```

## Мобильное приложение

В `frontend/.env.local` заменить адрес Render на свой домен и пересобрать APK:

```
VITE_API_URL=https://dragram.ru
VITE_WS_URL=wss://dragram.ru
```

```bash
npm run cap:android
```

Веб-версии это не касается: в Docker-образе `.env.local` удаляется, и фронтенд
ходит по относительным путям на тот же домен.

## Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| `init-letsencrypt.sh` падает на запросе сертификата | DNS ещё не обновился либо A-запись указывает не туда. Проверить `nslookup`, подождать, запустить скрипт снова |
| Приложение unhealthy, в логах ошибка подключения к БД | Неверные `DB_USER`/`DB_PASS`/`DB_NAME` в `.env` — или в пароле неэкранированный `$`, см. шаг 4 |
| Приложение unhealthy, в логах ошибка Redis `NOAUTH` | Не задан `REDIS_PASSWORD` в `.env` (или задан только для контейнера redis) |
| WebSocket отваливается через минуту | Между клиентом и сервером появился ещё один прокси (например, Cloudflare) — увеличить `TRUSTED_PROXY_COUNT` и проверить его таймауты |
| `docker compose pull` — permission denied | Сервер не авторизован в ghcr.io, см. шаг 5 |
| Ошибка вида `exec /app/entrypoint.sh: no such file or directory` | В git попали CRLF-переносы. Исправляется `.gitattributes`, при необходимости: `git add --renormalize . && git commit` |

## Бэкапы

Postgres теперь живёт на этом же сервере, поэтому его бэкапит `deploy/backup-db.sh`:
дамп кладётся локально в `/var/backups/dragram` и выгружается в Object Storage.
Поставить в cron (один раз):

```bash
sh /opt/dragram/deploy/install-backup-cron.sh
```

Проверить, что задание действительно стоит и отрабатывает:

```bash
crontab -l
sh /opt/dragram/deploy/backup-db.sh
```

**Бэкапы лежат в отдельном приватном бакете** (`S3_BACKUP_BUCKET`), не в том,
где медиа. Это не мелочь: дамп содержит хеши паролей, номера телефонов и
зашифрованные приватные ключи пользователей — то есть всю переписку, если его
не спеша расшифровать офлайн. Бакет с медиа раздаётся клиентам, и когда-то
дампы лежали в нём же.

`.env` стоит сохранить в надёжном месте отдельно: восстановить его содержимое
неоткуда.

## Хранилище файлов

Оба бакета должны быть с **ограниченным** доступом («Публичный» — нельзя).
Файлы раздаёт само приложение: `GET /media/<ключ>` проверяет, что пользователь
вошёл, и отвечает редиректом на presigned-ссылку с TTL 15 минут. Трафик при
этом идёт мимо сервера, напрямую из хранилища.

Проверить, что бакеты закрыты (ожидаем `403` в обоих случаях):

```bash
curl -s -o /dev/null -w "%{http_code}\n" "https://storage.yandexcloud.net/$S3_BUCKET/?list-type=2"
```

```bash
curl -s -o /dev/null -w "%{http_code}\n" "https://storage.yandexcloud.net/$S3_BACKUP_BUCKET/?list-type=2"
```

И что через сайт без авторизации ничего не отдаётся (ожидаем `401`):

```bash
curl -s -o /dev/null -w "%{http_code}\n" "https://$DOMAIN/media/uploads/test.jpg"
```

Ключи доступа стоит разделить: сервисный аккаунт приложения — только
`PutObject`/`DeleteObject`/`GetObject` на префикс `uploads/` основного бакета;
аккаунт бэкапов (`S3_BACKUP_ACCESS_KEY`/`S3_BACKUP_SECRET_KEY`) — только на
бакет бэкапов. Тогда утечка ключа приложения не даёт доступа к дампам базы.

Объём загрузок ограничен с двух сторон: потолок на файл (200 МБ для видео,
25 МБ для фото, 50 МБ для аудио — `src/chats/service.py`) и суточная квота на
пользователя (`UPLOAD_DAILY_QUOTA`, по умолчанию 1 ГБ). Если хочется ограничить
и рост хранилища во времени — в консоли Object Storage можно добавить
lifecycle-правило на удаление объектов из `uploads/` старше N дней. Учтите: для
мессенджера это означает, что старые фотографии в переписке перестанут
открываться.

## Дверь перед сайтом

Прежде чем показать форму входа, сайт спрашивает два ответа, известных только
своим. Проверка целиком на сервере и стоит до всех маршрутов (ASGI-middleware),
поэтому обойти её через `curl` по адресу вроде `/auth/login` нельзя — закрыты
и API, и websocket. Открыты без пропуска только оболочка приложения, её
статика и сами ручки `/gate`: без них дверь нечем было бы показать.

В `.env` лежат **только Argon2-хеши**. Ни в репозитории, ни в собранном образе,
ни на сервере правильных ответов нет, и из хешей они не выводятся. Задать:

```
uv run python deploy/make-gate-hashes.py
```

Скрипт спрашивает ответы скрытым вводом (в историю терминала они не попадают)
и печатает две строки для `.env`. После этого — `docker compose -f
docker-compose.prod.yaml up -d app`.

Ответы сверяются не буквально: регистр, лишние пробелы, «ё», порядок слов в
имени и формат даты («16 августа», «16.08», «16 авг 1970») значения не имеют.
На неверную попытку сервер отвечает одинаково, не подсказывая, какое из двух
полей не сошлось, и держит лимит в 5 попыток в час с адреса.

Чего эта дверь **не** делает: она не заменяет вход по паролю и не защищает от
того, кто ответы уже знает или кому их переслали. Ответы низкоэнтропийные —
это защита от случайного прохожего и поисковых роботов, а не от целенаправленного
подбора.

## Что проверить в чужих консолях

Это единственное, что нельзя настроить из репозитория:

- **Object Storage**: у обоих бакетов уровень доступа «Ограниченный», листинг
  закрыт (команды выше). Если сервер уже работал какое-то время со старой
  конфигурацией — **старые дампы из бакета с медиа удалить вручную** и считать
  их скомпрометированными: они были доступны по прямой ссылке.
- **Firebase**: у сервисного аккаунта из `FCM_CREDENTIALS_JSON` должна быть роль
  `Firebase Cloud Messaging API Admin`, а не `Editor`/`Owner` всего проекта.
- **Google Cloud → API и сервисы → Учётные данные**: ключ из
  `google-services.json` (он лежит в git, это штатно) ограничить по имени
  пакета `com.dragram.app` и SHA-1 подписи приложения.

## Отдельная роль в Postgres

Приложению не нужен суперпользователь. Создать роль с правами только на свою
схему (один раз, после первого запуска и миграций):

```bash
docker compose -f docker-compose.prod.yaml exec db psql -U postgres -d dragram -c "CREATE ROLE dragram LOGIN PASSWORD 'ЗАМЕНИТЬ'; GRANT ALL ON SCHEMA public TO dragram; GRANT ALL ON ALL TABLES IN SCHEMA public TO dragram; GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO dragram; ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO dragram;"
```

После этого поменять `DB_USER`/`DB_PASS` в `.env` и перезапустить приложение.
Смысл: SQL-инъекция, если она когда-нибудь появится, не даст выполнить
`COPY ... TO PROGRAM` и захватить сервер.
